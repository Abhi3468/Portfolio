DKG Bank — banking simulator

A Django and Django REST Framework project that explores safe account operations, API-first design, authentication, and the concurrency concerns behind financial workflows.

The problem

Banking operations are a useful way to learn that an apparently simple update can become unsafe when two requests arrive at once. This project was built to model account actions while keeping transaction logic, API endpoints, and the interface understandable.

  • Support account deposits, withdrawals, and PIN-related workflows.
  • Expose structured Django REST Framework endpoints alongside the web interface.
  • Prevent concurrent updates from taking an account balance below zero.
  • Record transaction and security events for diagnosis.

Architecture

Browser interface

HTML, CSS, and JavaScript provide the customer-facing workflow.

Django + DRF

Views and API endpoints handle authentication and banking actions.

Data layer

Django models persist account state; database transactions protect critical updates.

Key engineering decisions

Concurrency protection

Critical balance changes use Django transactions and row-level locking so concurrent requests are serialized safely.

API-first boundaries

DRF endpoints keep application operations available as structured JSON rather than coupling all logic to a template.

Abuse controls

Authentication-sensitive endpoints use throttling to limit repeated requests, alongside authentication and PIN checks.

Validation

The repository includes automated Django tests, including a multi-threaded concurrency test for withdrawal behaviour. A reviewer can run the documented test command locally and inspect the implementation directly.

This is a learning project and banking simulator—not a real financial product. It does not claim regulated compliance, production deployment, zero-downtime releases, or measured performance results.

What I learned

Reliability comes from explicit boundaries: make the update atomic, test the failure path, keep API behaviour clear, and avoid treating a database write as automatically safe under concurrency.
